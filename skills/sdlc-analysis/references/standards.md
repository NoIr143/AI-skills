# Requirements standards basis

Use these sources as a requirements-engineering framework. Tailor the SRS to project size, risk, contract, domain, and delivery model. Do not reproduce paid standard text or claim formal compliance.

| Source | Apply to this skill |
|---|---|
| [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html) | Structure requirements engineering across the life cycle; define stakeholder, system, software, interface, and quality requirements as managed information items. |
| [ISO/IEC/IEEE 12207:2026](https://www.iso.org/standard/90219.html) | Keep requirements connected to stakeholder needs and the broader software life-cycle processes, including verification, validation, operation, maintenance, and disposal. |
| [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html) | Use the nine-characteristic product-quality model to discover and classify relevant measurable quality requirements. |
| [ISO/IEC 25002:2024](https://www.iso.org/standard/78175.html) | Relate quality models to requirement definition, measurement, and evaluation rather than listing unmeasurable quality aspirations. |
| [NIST SP 800-160 Vol. 1 Rev. 1](https://csrc.nist.gov/pubs/sp/800/160/v1/upd2/final) | Derive security requirements from stakeholder protection needs and address them with appropriate rigor throughout the system life cycle. |
| [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) | For applicable web applications and services, use ASVS as a source of testable technical security requirements and record the selected ASVS identifiers. |

## Requirement-quality principles

- Identify the source, rationale, owner, priority, status, and release allocation.
- State one necessary and feasible obligation per requirement.
- Make the subject, behavior, condition, limits, units, and expected result unambiguous.
- Make verification possible through test, analysis, inspection, or demonstration with defined evidence.
- Maintain bidirectional traceability from stakeholder need through requirement and verification.
- Keep requirements implementation-independent unless a mandated interface, regulation, contract, or existing-system constraint requires otherwise.
- Baseline approved requirements and assess downstream impact before accepting changes.
