# Testing standards basis

Use these sources to structure risk-based testing and tailor them to project size, domain, technology, and release risk. Do not reproduce paid standard text or claim formal compliance.

| Source | Apply to this skill |
|---|---|
| [ISO/IEC/IEEE 29119-1:2022](https://www.iso.org/standard/81291.html) | Use consistent software-testing concepts and vocabulary. |
| [ISO/IEC/IEEE 29119-2:2021](https://www.iso.org/standard/79428.html) | Govern, manage, plan, design, execute, monitor, and complete testing through a risk-based process usable in any life-cycle model. |
| [ISO/IEC/IEEE 29119-3:2021](https://www.iso.org/standard/79429.html) | Structure test plans, test cases, execution records, incident reports, and completion reports as maintainable test information. |
| [ISO/IEC/IEEE 29119-4:2021](https://www.iso.org/standard/79430.html) | Select test design techniques suited to the behavior and risks under test. |
| [ISO/IEC 25010:2023](https://www.iso.org/standard/78176.html) | Use relevant product-quality characteristics to discover functional and non-functional test conditions. |
| [ISO/IEC 25040:2024](https://www.iso.org/standard/83467.html) | Define quality evaluation criteria, execution evidence, and defensible conclusions. |
| [NIST SP 800-115](https://csrc.nist.gov/pubs/sp/800/115/final) | Plan, conduct, analyze, and report authorized technical security tests while controlling assessment risk. |
| [OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/) | Map web application security tests to the project's selected, testable technical security requirements. |
| [OWASP Web Security Testing Guide](https://owasp.org/www-project-web-security-testing-guide/stable/) | Select practical web and API security test techniques and report them consistently. |
| [WCAG 2.2](https://www.w3.org/TR/WCAG22/) | Verify web interfaces against the accessibility level approved in the requirements. |

## Application principles

- Test priority follows product and project risk, not code coverage percentage alone.
- Expected results come from approved requirements, contracts, design, and accepted regression baselines.
- Static analysis, dynamic testing, exploratory testing, and human review provide complementary evidence.
- Security and performance testing require explicit scope, safe environments, monitoring, and stop conditions.
- Reproducibility requires revision, environment, data, commands, results, and sanitized evidence.
- A quality verdict is bounded by tested scope and residual risk; it is never a claim that defects do not exist.
