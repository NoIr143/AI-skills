# Standards basis

Use these sources as a planning framework. Tailor the resulting plan to project size, risk, contractual obligations, and delivery model. Do not reproduce paid standard text or claim formal compliance.

| Source | Apply to this skill |
|---|---|
| [ISO/IEC/IEEE 12207:2026](https://www.iso.org/standard/90219.html) | Use the common software life-cycle process framework and consider acquisition, supply, development, operation, maintenance, and disposal with stakeholder involvement. |
| [ISO/IEC/IEEE 24748-5:2017](https://www.iso.org/standard/60062.html) | Structure the software development plan, its information items, technical planning, control activities, communication, and cooperation across the complete life cycle. |
| [ISO/IEC/IEEE 29148:2018](https://www.iso.org/obp/ui/en/#iso:std:iso-iec-ieee:29148:ed-2:v1:en) | Keep stakeholder needs, system boundaries, requirements, interfaces, constraints, and acceptance evidence explicit and traceable. |
| [SWEBOK — Software Engineering Management](https://www.computer.org/education/bodies-of-knowledge/software-engineering/topics) | Cover project initiation and scope, deliverables, effort/schedule/cost estimation, resource allocation, and risk management. |
| [PMI Practice Standard for Project Estimating](https://www.pmi.org/standards/for-estimating) | Make estimates transparent, evidence-based, range-oriented, and suitable for predictive or adaptive delivery. Maintain an estimate basis and update it when assumptions change. |
| [ISO/IEC/IEEE 16085:2021](https://www.iso.org/standard/74371.html) | Integrate risk identification, analysis, treatment, ownership, monitoring, and continual improvement throughout the project life cycle. |
| [NIST SP 800-218 SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final) | Integrate secure development practices into the selected SDLC, assign security responsibilities, protect software and data, and plan evidence for security verification. |

## Tailoring principles

- Apply processes according to project context; a small internal tool does not need the same governance as regulated or safety-critical software.
- Preserve outcomes even when terminology changes. Agile teams may use a product backlog and release goals where predictive projects use a WBS and baselined plan.
- Treat scope, schedule, resource, quality, risk, and cost decisions as connected. Record the impact when one constraint changes.
- Plan operations, maintenance, and retirement when they affect architecture, staffing, data, contracts, or total cost of ownership.
- Keep facts, estimates, assumptions, risks, and decisions distinguishable so the plan can be reviewed and revised.
